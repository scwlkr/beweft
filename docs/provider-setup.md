# Connect your own social accounts

beweft talks to each network directly. You supply your own developer app and authorize your own destinations. Neither Buffer nor another social manager is a publishing backend. API access, provider review and costs remain your responsibility; installing an adapter does not grant them.

The direct adapters are fixture-tested, not live-qualified for your accounts. Read [capability research](research/provider-capabilities.md) for dated API rules and [connection design](research/connections.md) for the source review.

The production server exposes these connection and delivery handlers. The built-in UI's new shared-impact disconnect confirmation and removal-attestation flow still need their corresponding client update; its older unconfirmed disconnect request is rejected safely. Fixture coverage is not a claim of live qualification.

## Prepare the server

1. Set `BEWEFT_PUBLIC_URL` to your actual HTTPS origin. Do not add a path or invent a domain; it must route to this server.
2. Set `BEWEFT_ENCRYPTION_KEY` to a persistent random 32-byte key encoded as 64 hexadecimal characters. Keep it outside Git and back it up separately from the database. Losing it makes saved provider credentials unreadable.
3. For Mastodon or a custom Bluesky PDS, set `BEWEFT_ALLOWED_PROVIDER_ORIGINS` to comma-separated HTTPS origins approved by the operator. The default is `https://bsky.social`. Origins must use public DNS names and port 443. beweft resolves and pins public addresses for the operation and does not follow HTTP redirects. Private/local addresses are rejected.
4. Ensure your reverse proxy allows the configured upload size and long-running uploads. The media library persists on the server; worker processes need the same media volume.
5. Confirm worker health before filling queues. App sign-in, OAuth consent, successful publishing and receipt verification are separate checks.

## Set up a developer app

Open connection settings, choose the provider, then enter its client ID and secret. Saved secrets are never returned to the browser. Leaving an existing secret field omitted preserves it. Supply secrets through a password manager; never paste them into issues or logs.

Register exactly this callback pattern, replacing the origin and provider slug:

```text
https://your-real-host.example/api/v1/connections/x/callback
```

| Provider slug | Developer setup and destination |
| --- | --- |
| `x` | X developer app with OAuth 2 enabled, confidential web-app client, read/write and media permissions. Approve pay-per-use costs in the provider console first. |
| `youtube` | Google Cloud project with YouTube Data API enabled, OAuth web client and consent configuration. Authorize the Google identity owning the intended YouTube channel. Check the actual project quota and verification state. |
| `facebook` | Meta app with Facebook Login and Page permissions. Consent as a person who can create content on the Page, then choose that Page. Personal profiles are not Page destinations. |
| `instagram` | Meta Instagram Login app; Business or Creator account. This adapter uses the Instagram Login route, not a Facebook-linked personal account. |
| `threads` | Threads use case in a Meta app, Threads scopes and Threads identity. A Facebook token cannot substitute. |
| `mastodon` | Register an OAuth application on the operator-approved instance with the exact callback. Supply its client credentials and instance origin. |
| `linkedin` | LinkedIn app with OpenID Connect and Share on LinkedIn. This slice connects member profiles; organization access is a separate capability. |
| `pinterest` | Pinterest business developer account and reviewed trial/standard app access. Configure the exact callback and select an authorized board ID when composing. |
| `bluesky` | Save the configured PDS origin; client ID and client secret may be empty. Connect with handle and a dedicated app password. The password is exchanged for session tokens and is not retained. |

Exact scopes requested by the installed version are listed in `crates/providers/src/oauth.rs`. Optional analytics/comment scopes may require additional provider approval. If a developer app rejects a scope, correct its products/approval before reconnecting; do not assume a publishing-only grant enables the whole inbox.

## Connect and check the identity

Choose a brand, connect its channel, complete provider consent, and choose the returned destination. The flow expires after ten minutes and must finish in the browser session that started it. Starting another flow replaces that browser's temporary correlation cookie; finish one at a time. The UI reports authorization/identity confirmation without claiming publishing has been tested.

On reconnect, authorize the same external destination. A different Page/channel must be connected separately. Reconnect retains schedules and history; an intentionally paused channel stays paused. Disconnect cancels queued deliveries, removes local credentials and pauses the selected channel. Clients must warn before disconnect that other connected channels for the same provider, including unrelated accounts, can require reconnection. Their saved credentials, pause settings and queues are retained. The server requires explicit shared-impact confirmation before changing anything.

OAuth authorizations started before a disconnect must be started again after access removal. Disconnect never sends a provider revoke request; for every direct provider, the owner inspects existing channels, removes the affected access through the provider's access settings (such as connected apps or app passwords) and explicitly confirms completion before connecting again. Before taking removal steps, check the owner-only removal-status endpoint; if it reports another operation in progress, wait and recheck. The confirmation includes that pending removal UUID; an older UUID cannot clear a later removal. This confirmation is an owner attestation, not a provider receipt. Grant sharing is not reliably known, so a stored grant or an unhealthy/unknown direct grant even without saved credentials conservatively marks other connected channels for that provider as needing reconnection, including unrelated accounts. Their saved credentials, pause settings and queues are retained. An active delivery or reply on an affected channel blocks disconnect; an active sync must finish first. While a provider operation is in progress, wait for it to finish and retry to check the current status before removing access. An unresolved removal blocks new authorization and completion across that provider. Repeating a completed disconnect with no saved grant does not restart removal or affect channels reconnected since then; a still-pending removal remains pending. When there is no known or possible direct grant, inspect existing channels before removing only orphaned provider access. Google says [revocation removes the project's granted scopes and invalidates issued tokens for all clients in the project](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke) and may take time to have full effect; neither fixtures nor owner confirmation establish live propagation timing.

Callback code exchange and identity lookup hold the same provider gate as disconnect, and a flow from an older generation cannot begin an exchange after the removal boundary. Callback and Bluesky session admission read the remaining flow/browser-session lifetime from PostgreSQL, then bound their local network deadline with a one-second margin and a 60-second cap. They recheck the live session before storing a grant. A callback received while the gate is busy consumes that authorization; wait for the current operation or removal confirmation. An interrupted or timed-out exchange can still have created access remotely even when beweft stores no candidate. First inspect your connected channels for the destination: a completion response may have been lost. If it did not connect, check the provider's connected-app settings and remove only orphaned access before starting authorization again; shared provider access may serve other channels. Canceling a local request does not prove the provider canceled its work. Bluesky app-password session creation also holds the provider gate and is blocked while removal is unresolved; an interrupted session request may still have created a remote session.

## Current formats and observations

The provider catalog is authoritative for this installed slice. X publishes text, images or a single MP4 video; YouTube uploads a video with explicit privacy and audience; Facebook publishes text/a single image; Instagram publishes one JPEG/Reel; Threads publishes text/single image/video; Mastodon publishes text/media; Bluesky publishes text, up to four images, or one MP4 video; LinkedIn publishes member text; Pinterest publishes an image Pin. X threads, expanded Meta formats, Bluesky public replies, LinkedIn media and organizations, Pinterest reads and expanded formats, and Google Business Profile direct posting still need implementation. These are implementation limits to extend, not claims that the networks block all other formats. Unsupported formats return a clear error instead of dropping attachments.

Bluesky video processing happens before the public post is created. The server reads the account's authenticated DID document and derives the token audience as `did:web:` plus the PDS host, as in the official guide. Credentials are sent only to the configured, approved origin; the PDS address in that document is used for the token audience, not as a new credential destination. A custom PDS whose service DID does not follow that host convention may need manual handoff. The server streams the MP4 to Bluesky's video service and saves the processing job and resulting blob in the encrypted delivery checkpoint. A video's saved description becomes the embed's alt text. Captions are not yet supported. Bluesky-hosted accounts require a verified email, and account-level daily video limits apply; those requirements may change and access is not guaranteed by a successful connection. See the [official video guide](https://bsky.network/docs/about-bluesky-content/video/) and [video embed lexicon](https://github.com/bluesky-social/bsky/blob/main/lexicons/app/bsky/embed/video.json). The adapter is tested against isolated fixtures only.

X video uses the [current v2 chunked upload](https://docs.x.com/x-api/media/quickstart/media-upload-chunked): initialize, indexed 4 MiB append chunks, finalize, then status polling when processing is pending. Upload progress and processing delays survive bounded worker claims. This adapter accepts one MP4 up to 256 MiB and 0.5–1,200 seconds, H.264 progressive YUV 4:2:0 with square pixels, no more than 60 fps, a maximum longer side of 1,280 pixels and shorter side of 1,024 pixels, and optional mono/stereo AAC-LC. These are conservative local limits based on [X media guidance](https://docs.x.com/x-api/media/quickstart/best-practices); X can impose tighter account or entitlement limits. X image descriptions use its media metadata endpoint, but video descriptions are rejected until applicability is established. The app requires the relevant `tweet.write` and `media.write` grants. Fixtures demonstrate the local protocol only; no live publication has been qualified.

Remote-fetch formats (Meta and Pinterest) need your public HTTPS origin. beweft creates expiring capability URLs for only the media in that delivery; the authenticated media library remains private. Do not log or share capability URLs. YouTube uploads stream in 8 MiB chunks, saving the session and confirmed offset between requests. These checkpoints are encrypted and never returned by the public API.

Use channel sync to fetch a bounded recent page of available comments/mentions and observations for up to ten local published posts. X sync requires explicit metered-read acknowledgement. This is partial coverage, not a historical import or universal DM inbox. Missing metrics stay missing; the local workflow summary is not social engagement data. Replies are supported only where the catalog says so and have durable request IDs; reusing a request ID reads its result without sending twice.

Concurrent syncs share a per-server budget derived from its database pool, leaving one pool connection outside that budget. When the budget is full, a sync is rejected promptly and can be retried. A pool with only one connection cannot run syncs. This limits sync admission; unrelated operations can also use the remaining connection.

## Resolve failed or uncertain delivery

A definite provider rejection can be corrected and retried through the application. A lost response or worker interruption is **uncertain** and never automatically becomes another post. For YouTube, provider reconciliation probes the saved upload session and can resume confirmed partial progress. For Bluesky, automatic polling of a saved processing job has a 30-minute database-clock window; afterward, reconcile the saved job to check it and explicitly continue. At the public-write boundary, reconciliation queries the preassigned record URI and compares the complete frozen record, including its media and descriptions. A missing record is not proof it never existed and does not authorize another write. If an upload response was lost before its job ID was saved, the adapter cannot query that job or safely retry the same delivery automatically. Stop the original sender, inspect the provider, and make a deliberate new publication only after resolving the outcome. Other uncertain outcomes need inspection on the network and explicit owner reconciliation.

For X, the provider-status `x_upload` observation distinguishes upload progress from a possible public write for video, images, and text. Before reset, stop the original sender. An upload-only checkpoint can be reset with its current attempt and checkpoint IDs; an unknown public outcome (including a legacy image checkpoint) also requires inspecting X and recording a not-published owner attestation against those exact IDs. The owner must then explicitly reset and separately retry; neither status nor reset schedules a post. Retrying cannot bypass the checkpoint. A public request already accepted by X can remain uncertain even after the local sender stops. See the [API contract](api-contract.md) for the fields and conflict behavior.

TikTok is manual-only for this private self-hosted use case: its Direct Post intended-use rules exclude internal/private upload utilities. Download the media, copy the caption, finish on TikTok, then record completion and its URL. Manual confirmation is an owner attestation, not a verified API receipt.

Provider formats, permissions and pricing change. Do not run public test posts or paid calls merely to check setup. Use approved isolated test accounts/fixtures, and separately authorize any live qualification.

### Grant and audience safeguards

Each channel's `capabilities` describes the implemented adapter separately from `capabilities.permissions`. The latter reports provider-returned scopes and `granted`, `missing`, or `unknown` for each action. Missing required scopes block that action before a request. Unknown means the provider did not report enough scope information; it is not evidence of permission or successful publishing. Even a granted scope does not prove account eligibility or provider app review. Refresh preserves scope knowledge when the provider omits it.

A stored grant is bound to its original client ID and instance origin. Changing either requires authorization again. Tokens are never moved to the new origin. Federated destination IDs include their instance origin, so matching numeric IDs on two servers cannot reconnect one another. In-flight OAuth authorization also records its original app; configuration changes invalidate that flow. Existing pre-upgrade flows must restart.

Mastodon inbox items retain original visibility and the source author/mentioned participants. A reply to a direct **or followers-only** source is sent **directly to those participants**: using followers-only on the reply could disclose it to a different follower set. Public and unlisted sources retain their visibility. Replies cannot add `@` mentions; the server prefixes the preserved recipients and supplies `allowed_mentions`. Missing audience metadata requires a fresh sync or a reply on the network. This follows Mastodon's [status controller](https://github.com/mastodon/mastodon/blob/main/app/controllers/api/v1/statuses_controller.rb) and [posting service](https://github.com/mastodon/mastodon/blob/main/app/services/post_status_service.rb), including explicit visibility and unexpected-mention rejection.

Reply claims and channel disconnect share the channel transaction lock. An active reply additionally holds a per-conversation database execution guard until its outbound work and completion finish; disconnect, recovery and a new reply fail promptly while that guard is held. A reply past its stored delivery deadline becomes uncertain, never automatically resent. New claims use the database clock after any lock wait or refresh, and derive a suspend-inclusive elapsed budget from the remaining 90-second claim with a one-second margin. A response after the database deadline cannot install a provider receipt; it remains uncertain. Reusing its request UUID returns its existing result.

Recovery compares the revision from the owner's latest inspection. Before recording not-published, the owner must attest the original sender has stopped and inspect the provider. A database connection closing, a process being canceled, or a deadline expiring does not establish that a provider did not receive an already-started request. When the original execution cannot be verified as finished, stop its originating API process before making that attestation; provider acceptance can still remain unknown.

### Media inspection and recovery

Install `ffprobe` (the Compose image includes FFmpeg). Before a new direct-provider schedule or queued replacement commits, the server validates the selected snapshot using the adapter's local text, option and media rules. It inspects media bytes with a forced local container, disabled MOV external references, a file/pipe protocol allowlist, bounded output and no inherited credentials. One scheduling mutation has a 12-second inspection budget. Unsupported content is rejected; for request-ID scheduling that rejection is durably recorded and replays unchanged. An unavailable or timed-out inspector returns an error without committing a result. Receipt replay does not rerun these checks. Delivery inspects again because files or installed capabilities can change; account permissions and eligibility can also change before delivery. File-backed video is streamed after inspection; it is not loaded into RAM in full.

Current conservative adapter limits: X images 5 MiB; Bluesky images 2 MB and MP4 video 300 MB/10 minutes; Facebook image 10 MiB; Pinterest image 20 MiB; Instagram/Threads images 8 MiB; Mastodon images 16 MiB and video 99 MiB. Other video is bounded at 256 MiB. All formats are additionally bounded by the server upload setting, which defaults to 256 MiB. Images have a 40-megapixel/16384-pixel ceiling (Bluesky 4000×4000); Instagram photos require width 320–1440 and aspect ratio 4:5–1.91:1. Instagram video requires 3–900 seconds; Threads video at most 300 seconds; both require MP4 H.264/HEVC, optional AAC and width at most 1920. YouTube accepts inspected video up to 12 hours, subject to the actual channel's upload eligibility. These are this adapter's accepted envelope, not a claim that every provider/account has identical limits. Mastodon instances may impose stricter limits. Automatic transcoding is not implemented. GIF delivery is currently accepted only for Mastodon; animated media cannot be mixed with other attachments.

Sources: [Bluesky image lexicon](https://github.com/bluesky-social/atproto/blob/main/lexicons/app/bsky/embed/images.json), [X media guidance](https://help.x.com/en/using-x/posting-gifs-and-pictures), [Meta's Instagram Reels sample requirements](https://github.com/fbsamples/reels_publishing_apis/tree/main/insta_reels_publishing_api_sample), [Mastodon attachment limits](https://docs.joinmastodon.org/user/posting/#attachments). Provider validation still has the final say about account-specific eligibility.

A YouTube upload status probe returning 404 marks the saved session expired; it does **not** prove the video was never published. Inspect YouTube Studio and record the authoritative owner outcome. If recorded as not published, explicitly reset the expired session, then retry. Reset is rejected while uncertain, for a live session, or without a later not-published attestation. It never happens automatically. This follows [Google's resumable upload protocol](https://developers.google.com/youtube/data/guides/using_resumable_upload_protocol). Checkpoint updates and reconciliation transitions hold the publication lock; worker checkpoint writes additionally require the current live attempt UUID, protecting newer attempts from stale workers.

### Isolated regression checks

`python3 crates/providers/tests/fixtures.py` runs loopback HTTP adapter fixtures and generated media checks (requires FFmpeg). `python3 crates/server/tests/provider_integration.py` creates and removes a unique database in the existing development PostgreSQL container, then exercises OAuth replay/session/config binding, blocked callback exchanges and stale generations, all-provider owner-managed removal fences and stale reconnects, bounded concurrent syncs and token rotation, origin-aware reconnect, reply/disconnect races, stale-checkpoint fencing, concurrent reconciliation, and expired-session reset. `provider_router_worker.py` also runs the production router and separate worker against loopback fixtures. These test runners apply a loopback-only network sandbox; they currently fail closed on hosts without the verified macOS sandbox. They remove their generated media and test databases. These checks establish fixture behavior, not live provider qualification.

The server's `provider-fixtures` Cargo feature exists only for these tests. Fixture processes set `BEWEFT_REQUIRE_PROVIDER_FIXTURES=true`, `BEWEFT_ENABLE_FIXTURES=true`, and a loopback-only `BEWEFT_PROVIDER_FIXTURE_ORIGIN`. A standard build refuses to start if fixture mode is required or a fixture origin is supplied; a fixture build also refuses a missing opt-in or invalid/missing origin. Run `provider_fixture_preflight.py default` against freshly built default binaries and `provider_fixture_preflight.py feature` against freshly built fixture binaries. Serialize builds that change features, since they can replace the same output binaries. Never enable the fixture feature in a deployment build.

Before each provider stage the worker locks its channel, publication and attempt, verifies the original attempt UUID and live lease against PostgreSQL's wall clock, and reads the immutable snapshot. It holds the locks through the request and checkpoint update. A suspend-inclusive elapsed budget derived from the database's remaining lease (with a one-second margin) bounds each stage and its HTTP requests; it does not compare the database timestamp to the worker host's wall clock. A missing supported elapsed clock fails closed. Checks around transport polls cannot retract an operation already handed to the transport or accepted remotely, so a deadline or lost response remains uncertain. Reconnect waits for the active stage, so an old grant's 401 cannot invalidate a newly connected grant. Reads and writes performed inside a transaction reuse its connection; they do not depend on spare pool capacity.

Inbox reply history is durable and available read-only across browsers. New reply UUIDs cannot bypass an unresolved sending/uncertain attempt. If an uncertain reply cannot be reconciled through a provider API, the owner must inspect the network and record published or not-published with a note. This is labeled owner attestation, never provider confirmation, and never resends automatically.

New replies also carry the last acknowledged reply ID as an optimistic history watermark. If another browser completes a reply while an earlier request is delayed in transit, that delayed request is rejected with `reply_history_changed`, even though the newer reply is already terminal. A same-UUID retry still retrieves its original result. History order is durable claim order rather than transaction-start timestamps. Migration `0006_provider_reply_history.sql` adds this ordering; standard upgrades apply it automatically.

Publishing preparation uses separate committed phases. First, the original attempt and lease are checked under locks and any successful refresh-token rotation is committed immediately. Media capability URLs are then committed before the provider can fetch them through another HTTP/database connection. The worker reacquires the locks and rechecks the original attempt, lease and current grant before publishing; those locks remain through the request and checkpoint save. Reconciliation and reply claims likewise commit refresh separately from later fallible work. A missing checkpoint, inconclusive probe, media error or publishing timeout cannot roll back a completed token rotation.

Migration `0007_reply_delivery_deadline.sql` gives replies a durable delivery deadline. This prevents a transaction that waited for a lock or token refresh from making a newly sent reply appear expired. The callback-fetch and single-use refresh-token regressions exercise these transaction boundaries against real HTTP and PostgreSQL fixtures.

Migration `0013_reply_observation_revision.sql` adds a revision advanced on every reply mutation, including an executor finishing after an earlier uncertain observation. A stale inspection cannot be used to resolve that newer state.
