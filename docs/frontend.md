# Web workspace

The web app uses React, TypeScript, Tailwind, Zod response validation, and the shadcn-style Button/Dialog primitives built on Radix. The unicorn mark is original inline SVG. No proprietary interface assets or private account content are included.

Run `pnpm install`, then `pnpm build`. The Rust server serves `web/dist` at its configured public origin. `pnpm check` checks TypeScript. For Vite development, use `pnpm dev` and configure the API's public origin to the browser's development origin; its proxy targets port 3000. Production should serve UI and API from the same origin.

## Verification

`pnpm test:e2e` uses an existing development PostgreSQL container (default `beweft-dev-postgres`, port 55439), built `target/debug/beweft-server` and `beweft-worker`, and `web/dist`. The Python harness creates a unique database, random owner credentials and encryption key, and temporary media/output directories. It starts private server/worker processes on an ephemeral loopback port. Its finally block stops those processes, drops that database, and removes temporary media and test output. Environment overrides match the backend integration harness's `BEWEFT_TEST_DB_*` and `BEWEFT_TEST_POSTGRES_CONTAINER` names.

Pass Playwright arguments to the harness to run a focused scenario, for example `pnpm --filter @beweft/web test:e2e tests/brand-recovery.spec.ts`. To include the replacement worker-claim regression, run `BEWEFT_FIXTURE_DELAY_MS=30000 pnpm --filter @beweft/web test:e2e tests/replacement-recovery.spec.ts`; the delayed fixture uses no provider network.

The Playwright tests use bundled Chromium and always close it in `finally`; it does not launch installed Chrome or use a normal profile. Direct invocation refuses to mutate a server without the isolated-test environment flags. The main scenario exercises login, brand/channel creation, posting rules, idea-to-draft-to-queue, publishing details, media upload, unavailable analytics, theme choice, and phone calendar/composer. It sends no live provider calls and no public posts. Provider OAuth/publishing and metered reads require separate isolated adapter qualification and authorized account testing.

Rust-generated request types are consumed by draft creation/editing, idea creation/editing, scheduling, and media limits. Zod validates runtime responses and shows contract mismatches as errors. Shared contract output is generated by the backend; do not edit it by hand.

Regression scenarios cover archived-brand recovery with overlapping brand-list reads, failed fallback loads and unavailable provider or health metadata; removal of the last brand; late metadata after a switch; session expiration while reads are stalled; late schedule loads; a completed mutation after a brand switch; delayed analytics; channel-only drafts; filtered queue reordering; calendar day selection; and mobile focus trapping/Escape. These use real local API/database workflows; response delays and failures are controlled in the browser. Additional controlled provider-response fixtures verify partial-sync errors and counts, connection/reconnect controls, permission metadata, private Mastodon reply audience, owner-attestation receipts, and expired YouTube session reset without automatic retry. They prove UI behavior, not real provider access. Temporary test output is removed even after a failed assertion.

The brand and authentication follow-up passed `pnpm build` and all 55 isolated browser scenarios on 2026-10-29. After adding session guards to intent changes, 34 focused authentication, reply, and helper scenarios passed. A loopback HTTP/1 regression holds owner-response bodies while two reply dialogs and a third tab compete for the auth lock; it verifies completed logout and usable replacement checks. Further regressions hold intent locks through sign-out and preserve unknown outcomes. Fresh independent review remains required. Scheduling recovery is described below and remains subject to independent review. Provider connection and live inbox/publishing paths were not exercised against real accounts.

## Workflow scope

The following are explicit unfinished workflows, not external provider blockers:

- Ideas can be organized by stage, group, and tags, filtered on the board, edited, and converted to a draft. Deleting a group retains its ideas as ungrouped.
- Drafts can be duplicated, and reusable templates can be created from starters or saved drafts, edited, deleted, and applied with variables to create an unscheduled draft. Saved media, channel variants, and options are retained; choose an updated draft to replace template contents.
- Queued publications retain immutable revisions. The owner can edit the source draft, compare it with the queued snapshot, and explicitly replace that snapshot at its existing time. The canceled original stays in history. Queue-slot priority moves only queue-mode records; exact-date posts keep their times. A replacement with an unconfirmed response blocks new schedules while the original can still publish or be requeued. An audit-linked matching replacement resolves it; a known rejection or a terminal original requires an explicit review before scheduling is unlocked. The review never starts another publication.
- Manual handoff provides destination guidance, caption copying, per-file downloads, an optional published URL, and owner attestation. The owner publishes in the destination app and records the outcome here.
- Supported channel variants have separate text and media, and provider options. Media library descriptions are saved per asset and frozen into new scheduled snapshots; older snapshots retain their existing descriptions.
- YouTube exposes privacy, audience, synthetic-media disclosure, and category. It uses the post title as the public video title. License choice is not implemented.

Brand settings support rename, archive, and restore. Archive pauses channels; restored channels stay paused. Owner security lists and revokes sessions, revokes other sessions, and changes the password with a return to sign-in.

With the matching Meta and LinkedIn recovery contracts, the publication dialog reads the current attempt and checkpoint before a not-published attestation, requires confirmation that the sender stopped and the provider was inspected, and leaves retry as a separate action. Facebook Reel options appear only when the running channel catalog advertises Reel support; carousel selection follows ordered attachments. These controls do not establish live provider access.

Direct provider setup, destination selection, reconnection/disconnection, metrics, inbox read/reply, and explicit metered-X sync controls are implemented in the web client against the provider slice contract. This is not a claim that any live provider account or publication has been verified.

Manual channels choose a server-provided destination; changing it also changes guidance shown for existing handoffs. A destination-list outage leaves generic handoffs available and offers a retry. HTTPS links open the external platform and do not publish. The owner separately records the outcome. TikTok's private-tool path remains manual, and destinations without specific server guidance use the generic handoff.

Disconnect explains queue cancellation, credential removal and the potential impact on other accounts before the owner confirms. The server does not revoke provider access. The setup dialog checks provider removal status even if no app configuration exists, including after an unknown disconnect or confirmation response. Reconnection is blocked while removal is pending. The owner must inspect the affected channels, remove access at the provider, and explicitly attest to the current removal ID; a conflict requires a fresh status check and review.
Destination selection checks that the returned flow belongs to the selected brand and clears the dialog when the brand or session changes. A late response cannot complete a different browser selection.

With the matching X recovery contract, the publication dialog distinguishes an interrupted upload from a post request that may have started. The latter requires the owner to inspect X and attest that the original sender stopped for the displayed attempt and checkpoint before recording a not-published outcome. Reset uses those IDs and separate confirmation; it does not queue a retry. A status conflict triggers a fresh read and clears the prior choices. An older server without the X checkpoint field, or an unavailable status, leaves that boundary unknown and blocks recovery-dependent retry until it can be checked. These are owner attestations, not proof that a provider accepted or canceled a request. The X composer states the current adapter’s conservative video limits and that it rejects video descriptions.

Media details allow editing an asset's description, with the server's 2,000-character limit. The composer shows descriptions for each selected asset and uses them in its accessible preview. New scheduling snapshots freeze those descriptions; editing an asset later does not rewrite already queued content. Media edits use a required metadata version: the server rejects a stale version rather than overwriting a newer edit. Before sending, the browser stores the asset, version, and exact description under the authenticated owner and brand. If the response is lost, the editor stays read-only across navigation or reload until an authoritative per-asset read observes a later version, or the user explicitly retries the same conditional update. An unchanged version alone cannot prove a still-running write failed. A later version fences that write but does not identify its author; the editor shows the current value without claiming attribution. Intent storage and short same-asset Web Locks require a secure origin and working browser storage; the network request never holds those locks. Failed reads remain blocked and can be checked again. The active dialog announces confirmed saves and recovery status. Local browser tests use a real row lock, response loss, competing updates, failed reads, navigation, brand switches, and snapshot immutability.

Pending media edits are visible across the workspace and block scheduling when the asset is used by any selected channel variant. The composer checks storage and reads each affected asset under same-origin locks before scheduling; if the loaded description changed, it refreshes the display and requires another submission. Unavailable owner or intent storage blocks scheduling; a failed asset refresh blocks posts using that asset while unrelated media can still be scheduled. A malformed record under a canonical asset key also blocks only that asset and is retained, because its outcome is unknown. A key identifying the current owner and brand without a complete canonical asset scope, or a storage enumeration or read failure, blocks scheduling across the workspace. The displayed text is the last loaded description; independent browsers and API clients are outside this local lock boundary. NUL characters are rejected before creating a media intent. To recover an older NUL-containing intent, the owner explicitly checks it: only the server's specific NUL validation rejection for the identical stored payload permits release for correction. Generic errors and unchanged reads do not clear unknown outcomes.

An unknown schedule can remain in flight after a tab closes or reloads, so an ephemeral browser lock does not freeze its media descriptions. The composer records the complete effective media union and its versions with the saved schedule. The server checks those versions atomically when creating snapshots; later media edits either leave the approved snapshot intact or cause a definitive conflict that requires refreshed descriptions and another deliberate submission.

Idea-group reads are independent of the workspace's required collections. If group metadata is unavailable, existing ideas remain editable and their group assignment is preserved; the group read can be retried. The board supports keyboard-accessible stage changes and filters and stacks its columns on narrow screens. Browser tests cover group and tag editing, retained ideas after group deletion, outage recovery, and a delayed old-brand response.

## Reply recovery

The reply dialog reads `GET /inbox/:id/replies` before enabling a send and again before a new POST. Server attempts establish outcomes; sending or uncertain attempts block new replies. A pending request UUID and original text are stored on this browser, scoped by owner, brand, channel, and inbox item, before transmission. This survives closure/reload and permits only an explicit retry of the same request if no server attempt exists. Confirmed terminal results clear that local pending record. No credentials are stored there. A recovery read failure blocks sending.

`GET /inbox/:id/replies` returns owner-scoped durable rows including a revision; stale sending attempts appear uncertain without a provider call. The server atomically blocks a fresh request UUID while that conversation has a sending/uncertain attempt. Owner resolution sends the observed revision and, for `not_published`, an explicit sender-stopped attestation with the resolution and note. A changed revision or busy executor requires another history check and explicit review. This records the owner's attestation and never sends a reply; it is not provider confirmation. Browser fixtures exercise the contract separately from live provider qualification.

Reply intent claims are serialized between same-origin tabs with the Web Locks API (HTTPS or localhost). Recovery rereads the shared pending record before claiming any send, and a newly discovered intent must be explicitly reviewed/retried with its original UUID and text. Each new request sends `expected_last_request_id` from acknowledged server history; an HTTP 409 `reply_history_changed` blocks the original request until recovery and explicit review. Reviewing intervening history preserves the original UUID, changes only its acknowledged watermark, and does not send; a separate retry is required. Independent browser contexts are protected by the server's atomic watermark and unresolved-attempt checks.

Reply claims, history acknowledgments, and cleanup of confirmed attempts check the captured workspace session after waiting for the intent lock. Their brief local-storage changes also take the authentication lock, so they are ordered with same-origin sign-in and sign-out. A reply whose network outcome is unknown keeps its original pending record across a session change.

The composer disables its entire editing fieldset during save/schedule requests, including channel and media selection, provider options, variant tabs, text, and time inputs. A delayed real-save browser regression verifies that the submitted snapshot cannot be silently replaced by edits made while saving. Regression browser contexts reuse an in-memory isolated-owner session and renew it after revocation. The isolated test database's login counters reset between helper-based tests; the main workflow still verifies UI login separately.

## Recovery status

Brand and collection loading are independent of optional provider and health metadata. Metadata GETs have a five-second deadline covering response bodies and are canceled when superseded or when the brand or session changes. Other GETs also have deadlines; mutations are not automatically retried. A successful brand list can correct an earlier automatic fallback, while a manual brand choice invalidates earlier list reads. Collection results remain guarded by the selected brand and session. Browser regressions hold the fallback's follow-up read while a newer list removes it, and use a loopback HTTP/1 proxy with stalled metadata bodies to verify socket recovery and usable replacement content during a persistent outage.

Same-origin app tabs share a random, non-secret session epoch in browser storage. Sign-in and sign-out write a transition epoch under a Web Lock before sending the credential-changing request; a failed storage write prevents that request. Session verification takes the same lock, so another tab cannot bind the transition epoch to the old cookie. Owner checks have a five-second deadline covering both the lock queue and response body and are canceled on supersession or unmount; a failed reply recovery keeps sending disabled until an explicit check succeeds. A session check that times out behind a slow sign-in can be retried from the sign-in screen. A queued sign-out sends only if the epoch still matches the session its tab displayed when sign-out began. Other tabs clear old workspace and editor data and recheck the session, including after a failed sign-in. API results, workspace updates, actions and 401 invalidation are fenced by their captured session epoch, even before a storage event is delivered. Browser storage and Web Locks (HTTPS or localhost) are required; unavailable storage is reported and blocks authentication. A timeout or network failure during sign-out is reported because server-side revocation was not confirmed. Cookie changes made outside this app's same-origin sign-in and sign-out flows do not update the epoch and are outside this coordination boundary. A failed sign-in status check offers an explicit retry. A successful brand-list read is still needed to discover removal. These changes require fresh independent review before merge.

The composer stores an owner/brand-scoped request UUID, saved post and revision, sorted channel IDs, exact time or queue mode, and the complete approved media-version map before scheduling. Within its brand, a pending outcome keeps the editor read-only through close, reload, session changes, and returning from another brand; it is available from the workspace even when the post has left Drafts. A generic rejection, missing lookup, in-progress response, or transport error is inconclusive; the owner may explicitly retry the same immutable request. The owner can instead stop it: the server serializes that action with the original request and returns its existing result or creates a durable rejection that prevents a delayed original from scheduling. A lost stop response is recovered through the same receipt. The client validates the normalized request, six-digit timestamp precision, media map, outcome, and original publication coverage before clearing the record. Valid publication IDs are retained even when other row fields are missing or malformed; unbound IDs need independent owner-scoped verification. Every validated channel-to-publication binding is retained even from a partial response, and later observations must agree with it; an observed acceptance cannot be cleared by a rejected receipt. A failed receipt read after a successful POST remains unresolved. Publication summaries may reflect later rescheduling or cancellation, but recovery never follows replacement IDs. Older records without the media-version map remain available for inspection but cannot be retried or stopped safely here.

A definitive media-version conflict prompts the owner to stop the original request, refresh, and review before another schedule. A matching durable format-rejection receipt also unlocks correction with a new deliberate request. Before clearing a rejected request, the browser saves a separate owner-, brand-, and post-scoped correction preference for its queue choice or exact time, including seconds, fractional seconds, and offset. It restores that choice after close or reload until the owner deliberately changes it; the preference contains no pending request, post snapshot, or media map. A damaged preference requires an explicit time or queue choice; unavailable storage prevents scheduling until it can be checked. If another choice appears during recovery, the composer shows both choices and lets the owner explicitly retain the original, after which the original request still needs to be checked or stopped. Preference changes and clearing are session-fenced and compare the previously observed value, so stale tabs cannot erase a newer choice. A request-ID or receipt mismatch remains locked for recovery, even after a later stale response or reload. Storage readback and session-fenced Web Locks protect local intent changes; clearing compares the full saved immutable snapshot and every observed channel binding. Older ID-only observations are checked against compact, owner-scoped publication summaries before they can be cleared; an unavailable check leaves them locked. Media locks are held only through the preflight read, with the server's version precondition protecting the subsequent snapshot. The preview identifies when its currently loaded media differs from the original schedule.

Isolated browser tests against the real API and PostgreSQL exercise a committed response lost before reload and same-ID retry; partial POST and GET observations, conflicting channel bindings, legacy ID-only verification, and exact-time correction; a generic 400 and 404 while the original transaction is held; retirement before a delayed POST, a busy original, an accepted original, and a lost retirement response; original canceled/replaced and past-time replay; queue-to-exact rescheduling; media edits before channel admission and after snapshot locks; and effective media across selected variants including an explicit empty override. Controlled fixtures cover incomplete or mismatched receipts, microsecond and media-map mismatches, a stale failure after a conflict, changed same-ID snapshots, unavailable storage, legacy records, and cross-tab session transitions. A loopback-only provider fixture exercises local format rejection without provider traffic. These tests do not establish live provider access.
