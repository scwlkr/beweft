# Web workspace

The web app uses React, TypeScript, Tailwind, Zod response validation, and the shadcn-style Button/Dialog primitives built on Radix. The unicorn mark is original inline SVG. No proprietary interface assets or private account content are included.

Run `pnpm install`, then `pnpm build`. The Rust server serves `web/dist` at its configured public origin. `pnpm check` checks TypeScript. For Vite development, use `pnpm dev` and configure the API's public origin to the browser's development origin; its proxy targets port 3000. Production should serve UI and API from the same origin.

## Verification

`pnpm test:e2e` uses an existing development PostgreSQL container (default `beweft-dev-postgres`, port 55439), built `target/debug/beweft-server` and `beweft-worker`, and `web/dist`. The Python harness creates a unique database, random owner credentials and encryption key, and temporary media/output directories. It starts private server/worker processes on an ephemeral loopback port. Its finally block stops those processes, drops that database, and removes temporary media and test output. Environment overrides match the backend integration harness's `BEWEFT_TEST_DB_*` and `BEWEFT_TEST_POSTGRES_CONTAINER` names.

Pass Playwright arguments to the harness to run a focused scenario, for example `pnpm --filter @beweft/web test:e2e tests/brand-recovery.spec.ts`.

The Playwright tests use bundled Chromium and always close it in `finally`; it does not launch installed Chrome or use a normal profile. Direct invocation refuses to mutate a server without the isolated-test environment flags. The main scenario exercises login, brand/channel creation, posting rules, idea-to-draft-to-queue, publishing details, media upload, unavailable analytics, theme choice, and phone calendar/composer. It sends no live provider calls and no public posts. Provider OAuth/publishing and metered reads require separate isolated adapter qualification and authorized account testing.

Rust-generated request types are consumed by draft creation/editing, idea creation/editing, scheduling, and media limits. Zod validates runtime responses and shows contract mismatches as errors. Shared contract output is generated by the backend; do not edit it by hand.

Regression scenarios cover an archived active brand with a failed fallback load or failed/stalled provider and health reads, removal of the last brand, late metadata after a brand switch, late schedule loads, a completed mutation after a brand switch, delayed analytics, channel-only drafts, filtered queue reordering, calendar day selection, and mobile focus trapping/Escape. These use real local API/database workflows; response delays and failures are controlled in the browser. Additional controlled provider-response fixtures verify partial-sync errors and counts, connection/reconnect controls, permission metadata, private Mastodon reply audience, owner-attestation receipts, and expired YouTube session reset without automatic retry. They prove UI behavior, not real provider access. Temporary test output is removed even after a failed assertion.

`pnpm build` and all twenty isolated browser scenarios, including brand recovery, passed on 2026-10-29 after the `ef3120a` checkpoint; fresh independent review remains required for the fallback fix. The scheduling-intent changes remain unwired and unverified. Provider connection and live inbox/publishing paths were not exercised against real accounts.

## Scope still requiring subsequent slices

The following are explicit unfinished workflows, not external provider blockers:

- Ideas have title, notes, color, search, editing, and conversion to a draft. Board columns/status groups and tags are not implemented.
- Draft duplication is implemented. Reusable custom templates and a template library are not implemented.
- Queued publications retain immutable revisions and can be canceled, reordered in queue mode, and rescheduled. Editing their content with an atomic revision replacement is not implemented; editing a source draft does not silently rewrite queued history.
- Manual handoff provides caption copying, per-file downloads, an optional published URL, and owner attestation. Network-specific launch links and guidance need a target-platform field on manual channels.
- Supported channel variants have separate text and media, and provider options. Current Bluesky/Mastodon alt text is one description per channel variant applied to all images. Per-media descriptions need a richer schema.
- YouTube exposes privacy, audience, synthetic-media disclosure, and category. It uses the post title as the public video title. License choice is not implemented.

Direct provider setup, destination selection, reconnection/disconnection, metrics, inbox read/reply, and explicit metered-X sync controls are implemented in the web client against the provider slice contract. This is not a claim that any live provider account or publication has been verified.

## Reply recovery

The reply dialog reads `GET /inbox/:id/replies` before enabling a send and again before a new POST. Server attempts establish outcomes; sending or uncertain attempts block new replies. A pending request UUID and original text are stored on this browser, scoped by owner, brand, channel, and inbox item, before transmission. This survives closure/reload and permits only an explicit retry of the same request if no server attempt exists. Confirmed terminal results clear that local pending record. No credentials are stored there. A recovery read failure blocks sending.

`GET /inbox/:id/replies` must return owner-scoped durable rows `{id,inbox_id,text,state,receipt,error,created_at,updated_at}`, including unresolved attempts; stale sending attempts appear uncertain without a provider call. The server must atomically block a fresh request UUID while that conversation has a sending/uncertain attempt, since browser checks alone cannot prevent concurrent-tab races. Explicit owner resolution uses `POST /inbox/:id/replies/:request_id/resolve` with `{resolution:"published"|"not_published",note,external_url?}` and returns the durable row. This records an attestation and never sends a reply. These endpoints belong to the coordinated provider slice; browser regression fixtures exercise the client contract separately from live provider qualification.

Reply intent claims are serialized between same-origin tabs with the Web Locks API (HTTPS or localhost). Recovery rereads the shared pending record before claiming any send, and a newly discovered intent must be explicitly reviewed/retried with its original UUID and text. Each new request sends `expected_last_request_id` from acknowledged server history; an HTTP 409 `reply_history_changed` blocks the original request until recovery and explicit review. Reviewing intervening history preserves the original UUID, changes only its acknowledged watermark, and does not send; a separate retry is required. Independent browser contexts are protected by the server's atomic watermark and unresolved-attempt checks.

The composer disables its entire editing fieldset during save/schedule requests, including channel and media selection, provider options, variant tabs, text, and time inputs. A delayed real-save browser regression verifies that the submitted snapshot cannot be silently replaced by edits made while saving. Regression browser contexts reuse one in-memory isolated-owner session to avoid exhausting the real sign-in limiter; the main workflow still verifies UI login separately.

## R4 recovery status

Automatic brand fallback processes the brand list without waiting for provider or worker-health metadata. It uses `chooseBrand`, the same centralized transition as manual selection: it invalidates in-flight loads, clears all brand collections and the composer, resets feedback/search, and records the selected brand. Isolated browser regressions cover a failed replacement load, failed or stalled metadata, removal of the last brand, and late responses. Fresh independent review remains required.

The scheduling lost-response finding remains **unfixed in the running UI**: `useComposer` still saves/PATCHes a new revision on another scheduling submission. Two new, unused modules (`scheduleIntent.ts`, `usePendingSchedule.ts`) prepare owner/brand-scoped local intent storage, an immutable saved post snapshot/version/channel set/mode/time, serialized claims, authoritative publication inspection, and same-version scheduling. They are not connected to `useComposer` or a recovery view/banner. Do not describe their presence as a completed safety fix.

Remaining integration: block editor/new-revision actions while an intent is pending or recovery cannot be read; persist the intent before crossing the schedule network boundary; on unknown outcomes retain it through close/reload and offer read-only outcome checks plus explicit same-version resume (never PATCH before retry); restore a discoverable recovery panel even when the post has left Drafts. Successful/matching publication rows, including canceled outcomes, must be acknowledged without resending. A 409 may mean an existing publication or changed revision and must be reconciled. No rows alone do not prove an in-flight request failed. Definitive first-attempt 4xx rejection can permit returning to the saved draft after inspection; later rejection must not erase prior uncertainty. A changed post version can fence an old schedule only with a subsequent publication read. Partial recorded channel sets must remain visibly blocked rather than being blindly resubmitted. Validate response coverage before clearing an intent, and condition storage updates/removal on intent identity under the lock. Add real-API tests dropping a committed schedule response and reopening/reloading: exactly one publication and no new revision; also test delayed/no-record resume.
