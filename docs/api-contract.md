# beweft API contract

Additional implemented content and account workflows are specified in [workflows-api.md](workflows-api.md).

Base `/api/v1`. Success `{ "data": ... }`; failure `{ "error": { "code": "...", "message": "..." } }`. Lists return arrays in `data`. IDs are UUID strings; timestamps RFC3339 UTC. JSON requests set `Content-Type: application/json` and `X-Beweft-Request: 1`. Browser calls use cookie credentials. State-changing browser requests must have matching Origin when present; authenticated cookie mutations require the custom header. All endpoints except auth/status, auth/bootstrap and auth/login need authentication. API tokens use `Authorization: Bearer ...`. Read APIs accept valid tokens except token management; writes need the listed scope. Token listing/creation/revocation and logout require an owner cookie session and reject bearer tokens, including admin tokens. Tokens may restrict `brand_ids`; UI sessions have all owner access.

The following stable codes identify correctable rejections. They leave no
committed post, media record or publication from the rejected request. An
upload's temporary reservation and partial file are cleaned up asynchronously:

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | `post_text_too_long` | Post or channel-variant text exceeds 100,000 bytes. |
| 400 | `unsupported_media_type` | The file signature is not JPEG, PNG, GIF, WebP, MP4 or WebM. |
| 400 | `missing_posting_schedule` | A queued channel has no posting rules. |
| 400 | `provider_format_invalid` | The selected direct adapter cannot publish the locked snapshot's text, options or media. A request-ID schedule records this terminal rejection. |
| 503 | `provider_format_check_unavailable` | Local media inspection could not run or finish; no new publication or receipt was committed. |
| 409 | `posting_slots_unavailable` | No posting-rule slot is free in the next 60 days. |
| 409 | `post_version_conflict` | The submitted post version is stale. |
| 409 | `schedule_request_conflict` | A request UUID already identifies another scheduling intent for this owner. |
| 409 | `schedule_request_retired` | This exact request was retired before publication and cannot later be accepted. |
| 409 | `media_version_conflict` | The submitted media-version map is incomplete, extra, invalid, unavailable or stale for a newly admitted scheduling intent. |
| 400 | `invalid_cursor` | A list cursor is malformed or incompatible with its filters or scope. |
| 400 | `invalid_page_limit` | A parsed unsigned 32-bit list limit is outside 1–10. |

Existing `unauthorized` (401) and `forbidden` (403) codes indicate authentication
or access denial. A 401 after a write does not always establish its outcome:
bootstrap can create the owner before session creation fails. Other failures
retain their existing codes. A transport failure, interrupted response or unknown
error after a write likewise does not establish its outcome.

## Bounded list inspection

GET `/posts`, `/media`, and `/publications` accept optional `limit` (an integer
from 1 to 10) and `cursor`. Parsed unsigned 32-bit limits outside that range
return `invalid_page_limit`; malformed, negative, or greater-than-4294967295
query values return `invalid_request` instead. Use an integer from 1 to 10 for
either error. A request with `limit` returns `{data:[...],next_cursor:string|null}`;
the cursor is null on the last page. Supply the returned cursor with a limit and
the same route, filters, view, and authorized brand scope. Malformed or
incompatible cursors return 400. A cursor is opaque and limited to 2048
characters; it does not grant access. Every page applies authorization and
brand filters before pagination. Pages use `created_at DESC, id DESC`, with
the UUID breaking timestamp ties. They are live views rather than snapshots;
refresh from the beginning after concurrent changes. Without `limit`, existing
list order and response shape remain unchanged for the web application.

- `/posts` additionally accepts `status=draft` and `view=summary`. The summary
  is `{id,brand_id,title,text,media_ids,version,status,created_at,updated_at}`;
  variants and options are omitted. GET `/posts/:id` returns the full post.
- `/media` returns the normal media record on each page.
- `/publications` additionally accepts `group=queue|history`, `view=summary`,
  and `id=UUID`. Queue means queued/sending; history means every other state.
  The summary is `{id,post_id,brand_id,channel_id,channel_name,provider,post_version,scheduled_at,scheduling_mode,state,created_at,updated_at}`;
  payload and external/error fields are omitted. In every publication summary,
  including schedule responses and request recovery, `channel_name` is truncated
  to 100 Unicode characters and `provider` to 64. UUIDs and request identity are
  unchanged. GET `/publications?id=UUID&limit=1` without `view=summary` reads one
  full, authorized record, including its original channel name and provider.

The generated OpenAPI and TypeScript include the optional filters, compact
projections, and paged response envelopes.

## Authentication
- GET `/auth/status` → `{initialized:boolean}`.
- POST `/auth/bootstrap` `{setup_secret,email,password}` → `{id,email}` + session cookie. Password minimum 12 characters. Setup secret is `BEWEFT_SETUP_SECRET` on server. Only available before first owner.
- POST `/auth/login` `{email,password}` → `{id,email}` + session cookie.
- GET `/auth/me` → `{id,email}`.
- POST `/auth/logout` `{}` → `{ok:true}`. Owner cookie session only.
- GET `/tokens` → token metadata array. Owner cookie session only.
- POST `/tokens` `{name,scopes:["read","drafts:write","publishing:write","admin"],brand_ids?:[]}` → `{id,token,name,scopes,brand_ids}`. Secret returned once. Owner sessions only.
- DELETE `/tokens/:id` → `{ok:true}`. Owner cookie session only.

## Brands and connections
- GET `/brands`; POST `/brands` `{name,color?:"#8b5cf6"}` → brand. Admin write.
- Brand `{id,name,color,archived_at,created_at}`. Archived brands are hidden unless include_archived=true.
- GET `/providers` → capability descriptors. Provider status truthfully distinguishes implementation, configuration, execution, and verification; unavailable adapters cannot be connected.
- GET `/channels?brand_id=UUID`; POST `/channels` `{brand_id,name,provider:"manual",timezone?:"America/Chicago"}` → channel. Admin write. `fixture` is accepted only with explicit server opt-in and remains labeled fixture.
- PATCH `/channels/:id` `{name?,paused?,timezone?}` → channel. Admin write.
- Channel `{id,brand_id,name,provider,timezone,paused,capabilities,created_at}`. Manual channels require owner completion; they never claim automatic publication.

## Ideas and drafts
- GET `/ideas?brand_id=UUID`; POST `/ideas` `{brand_id,title,text?:"",color?:"lavender"}` → idea. PATCH `/ideas/:id` `{title?,text?,color?}`; DELETE `/ideas/:id`.
- Idea `{id,brand_id,title,text,color,created_at,updated_at}`.
- GET `/posts?brand_id=UUID`; GET `/posts/:id`.
- Post responses render base `media_ids` and variant `channel_id` and `media_ids` in canonical lowercase hyphenated UUID form, including older drafts stored with other valid UUID spellings. Other stored fields and existing publication snapshots are unchanged. New snapshots use canonical media IDs.
- POST `/posts` `{brand_id,title?:"",text,media_ids?:[],options?:{},variants?:[{channel_id,text?,media_ids?,options?}]}` → post.
- PATCH `/posts/:id` `{version:number,title?,text?,media_ids?,variants?,options?}` → post. Version required for conflict protection. Existing publication snapshots do not change; edit and schedule a new revision explicitly.
- DELETE `/posts/:id` deletes only drafts with no publications. Other posts remain as history.
- Post `{id,brand_id,title,text,media_ids,variants,options,version,status,created_at,updated_at}`. Status is draft/scheduled/published/attention derived from publications.
- Idea/post/media writes require `drafts:write`.

## Media
- GET `/media?brand_id=UUID` → media array.
- GET `/media/limits` → `{max_upload_bytes,quota_bytes,used_bytes,reserved_bytes,available_bytes}`. Storage quota defaults to 10 GiB (`BEWEFT_MEDIA_QUOTA_BYTES`); active uploads reserve capacity atomically. Uploads have a 15-minute deadline.
- POST `/media?brand_id=UUID` multipart field `file` → media. Exactly one field named `file` is accepted; extra or duplicate fields are rejected. The complete multipart request, including any epilogue, is consumed within the request body limit (the configured file limit plus 1 MiB) and the 15-minute deadline before a media record is committed or a signature rejection is returned. Maximum file size is `BEWEFT_MAX_UPLOAD_BYTES` (default 256 MiB), streamed to persistent storage; JPEG/PNG/WebP/GIF/MP4/WebM only. Authentication plus custom header applies to multipart too.
- GET `/media/:id/file` → authenticated file bytes.
- DELETE `/media/:id` → `{ok:true}`; media referenced by draft or publication cannot be removed.
- Media `{id,brand_id,name,mime,size,url,alt_text,created_at}`; `url` is the authenticated file endpoint.

## Scheduling and outcomes
- GET `/schedules?channel_id=UUID` → posting rules array.
- POST `/schedules` `{channel_id,days:[1,2,3,4,5],time:"09:00",timezone:"America/Chicago"}` → rule. Monday=1, Sunday=7. DELETE `/schedules/:id`. Each rule `{id,channel_id,days,time,timezone,created_at}`.
- POST `/posts/:id/schedule` `{version:number,channel_ids:[UUID],scheduled_at?:RFC3339|null,request_id?:UUID,media_versions?:{[UUID]:number}|null}` → publication array. Requires `publishing:write`. New clients should generate and persist a request UUID before sending and reuse it for that exact intent; omission remains supported for legacy clients. Channels must be unique and are normalized in UUID order. An exact time accepts at most six fractional-second digits, rejects leap seconds and higher precision, and is normalized to UTC microseconds; omit or pass null to reserve each channel's next posting-rule slot. For a new intent, the locked draft version must match and the exact time must be future (up to five seconds grace); all variants, the normalized request and original publication IDs commit atomically. Replaying the same owner/request UUID and normalized intent returns the original publication identities, with their current states, even after cancellation, replacement, archive, a draft edit or the time passing. Reusing it for a different post, version, channels, exact time or media-version map returns `schedule_request_conflict` (409). When supplied, `media_versions` must map exactly the union of media used by the selected channels to their positive metadata versions (at most 1,000 entries). Each selected variant's explicit media list overrides the draft's base list, even when empty; unselected variants do not contribute. The server acquires selected channel locks first, then locks all effective media in UUID order and checks the supplied versions in the snapshot transaction before writing publications. Missing, extra, nonpositive, unavailable or stale entries return `media_version_conflict` (409). When a request ID is present, this check runs only after request-key admission and checking for an existing receipt. Omitted or null means legacy behavior without a version precondition; `{}` is an explicit empty map and is distinct from null. A competing same-key request is rejected promptly with `schedule_request_in_progress` (409); the original outcome remains unresolved, so check status or retry the same UUID after it finishes. Optional `?view=summary` returns bounded publication summaries; the default returns full publications. View is not part of intent.
- GET `/schedule-requests/:request_id` → `{request_id,post_id,brand_id,request:{version,channel_ids,scheduled_at,media_versions},outcome:"accepted"|"rejected",error:{code,message}|null,publications:[PublicationSummary]}`. Existing accepted receipts have null error and their original IDs in channel order with current row states; a rejected receipt has a `provider_format_invalid` or `schedule_request_retired` error and no publications. A rejected receipt retains its original post UUID even if the unpublished draft is deleted; authorized recovery and same-ID rejection replay still work. The stored request timestamp is null or a UTC RFC3339 string with exactly six fractional digits. `media_versions` is the original canonical UUID-keyed map or null, not a read of current versions. Full publication detail is available separately through `/publications?id=UUID&limit=1`. Owner and brand restrictions apply. Missing and unauthorized IDs both return 404; a 404 while a POST is in flight is inconclusive and does not prove it failed. Preserve the intent until the committed result is known; never infer from a missing lookup that it is safe to create a different UUID.
- POST `/schedule-requests/:request_id/retire` `{post_id,brand_id,version,channel_ids,scheduled_at?:RFC3339|null,media_versions?:{[UUID]:number}|null}` → the scoped receipt above. Supply the exact saved scheduling intent; channel order and timestamps normalize as on scheduling. Under the same nonblocking request gate, an existing matching accepted or rejected receipt is returned unchanged. If no receipt exists and the authorized draft still exists, the server commits a `schedule_request_retired` rejection with no publications; any delayed original or replay receives 409 with that code. Retirement never cancels an accepted publication and does not validate formats or contact a provider. `schedule_request_in_progress` (409) means another operation still owns the gate; wait and retry or check status. A mismatched intent returns `schedule_request_conflict` (409). Missing and unauthorized draft/receipt return 404; in particular, a deleted draft with no receipt cannot be safely attributed to a brand and is not retired. A lost retirement response is resolved by reading the same request ID.
- Before a new direct-provider schedule or queued replacement commits, the server runs the adapter's static text, option, media format and local byte inspection against each selected snapshot. Inspections share a 12-second local budget; no provider or paid request occurs. A specific invalid result is `provider_format_invalid` (400); a request-ID schedule atomically records that rejection and no publications, and the same ID and intent always replays the same rejection, even if capabilities or configuration later change. Corrected work needs a new reviewed intent and request ID. An unavailable or timed-out inspector returns `provider_format_check_unavailable` (503) without a receipt or publications. Existing request-ID receipts replay before these checks. Manual, fixture and legacy unknown-provider channels retain their prior behavior. Account permissions, provider availability and eligibility can still change before delivery.
- GET `/publications?brand_id=UUID&channel_id=UUID` → publication array, earliest first. Optional filters.
- Publication `{id,post_id,brand_id,channel_id,channel_name,provider,post_version,scheduled_at,scheduling_mode,state,payload,external_id,external_url,last_error,created_at,updated_at}`. `payload` contains immutable `{text,media_ids,title,options}`. States: queued, sending, manual_required, published, failed, uncertain, canceled. Fixture success uses `fixture_complete`, never published.
- GET `/publications/:id/attempts` → durable attempts array with state and errors.
- POST `/publications/:id/cancel` `{}` → publication; only queued/manual_required/failed may cancel.
- POST `/publications/:id/manual-complete` `{external_url?:URL,note?:string}` → publication. Manual_required only; owner attestation stored, no verified provider receipt implied.
- POST `/publications/:id/reconcile` `{resolution:"published"|"not_published",external_id?:string,external_url?:URL,note:string,observed_attempt_id?:UUID,observed_checkpoint_id?:UUID,sender_stopped?:boolean,provider_inspected?:boolean,thread_ids?:string[],thread_root_definitively_ended?:boolean}` → publication. Uncertain only, except that an already-failed X public-boundary or Meta checkpoint may be re-attested as not published, and an already-failed X thread may be attested complete. For an X public-boundary/legacy image checkpoint or any Meta checkpoint, not-published requires an owner session, both current observed IDs, and both attestations true; this commits the attestation against that exact checkpoint. Published result is owner-confirmed reconciliation. Not-published becomes failed; X also requires the reset below. Explicit retry of a failed Meta checkpoint records its prior provider identifiers and starts a new session; public-boundary retry requires the current attestation. For a possibly accepted Facebook Reel or Page video, `provider_inspected:true` means the owner confirmed the remote operation definitively failed, was stopped, or was canceled; an absent post or a stopped local sender alone is not proof.

  X threads use a channel variant `options.x_thread:{replies:string[]}` containing 1–9 nonblank text-only replies, each at most 280 Unicode characters. Unknown keys and non-X use are rejected; the immutable publication snapshot contains the ordered replies. Root media uses the existing media snapshot. Completion with `thread_ids` requires an owner session, note, current observed attempt/checkpoint IDs, `sender_stopped:true`, and `provider_inspected:true` after inspecting the actual complete chain. IDs must be unique numeric IDs, cover every requested segment in order, and match the confirmed prefix. The server derives the root ID and canonical URL and rejects conflicting values. Root not-published requires `thread_root_definitively_ended:true`, explicitly affirming that the exact remote root operation definitively ended without creating a post. It is accepted only for a current `x_thread_post_started` checkpoint with explicitly empty confirmed IDs and `next_index:0`, together with the current attempt/checkpoint IDs, sender-stopped and provider-inspected attestations, and a note. Legacy or malformed progress cannot authorize reset. A separate reset and retry are needed. A known prefix blocks whole-thread not-published/reset. Owner attestation is not provider proof; absent content or a stopped local sender alone is not proof a remote operation ended.
- POST `/publications/:id/retry` `{}` → publication. Failed only, resets schedule to now and enqueues a new attempt. No automatic uncertain retries.
- POST `/queue/reorder` `{channel_id,publication_ids:[UUID...]}` → publication array. Complete list of that channel's `state=queued, scheduling_mode=queue` publications required. Exact-date publications are excluded and keep their dates. Preserves allocated queue slots and changes ordering transactionally.
- POST `/publications/:id/reschedule` `{scheduled_at:RFC3339}` → publication. Queued/manual_required only, optimistic state checks. Sets scheduling_mode to exact.
- Publication and schedule mutations require `publishing:write`.

## Direct provider connection slice

Provider app configuration and connection flows require an owner browser session, not an API token. Secret values are accepted once and never returned. Provider grants are encrypted server-side. Network access in these flows is real authorization/identity lookup; provider costs can apply. Adapter coverage remains fixture-tested and unverified with live accounts.

- GET `/provider-apps` → `[{provider,client_id,instance_url:string|null,configured:boolean,updated_at,revocation_id:UUID|null}]`. The removal ID here is a snapshot; check the admitted removal-status route before taking removal steps. `configured` requires a decryptable saved configuration and server key.
- PUT `/provider-apps/:provider` `{client_id,client_secret?,instance_url?}` → `{provider,client_id,instance_url,configured:true,callback_url}`. Omitted secret preserves the saved value; empty secret is rejected. Bluesky can use empty client ID/secret and defaults its instance to `https://bsky.social`, an entryway; video delivery requires the account's actual PDS origin to be configured. An existing connection cannot be rebound to a different origin under the same channel ID. Mastodon/Bluesky instances must match server `BEWEFT_ALLOWED_PROVIDER_ORIGINS` and resolve only to public IP addresses. Other providers reject instance URLs.
- POST `/connections/:provider/start` `{brand_id,reconnect_channel_id?:UUID|null}` → `{authorization_url,flow_id}` plus a separate HttpOnly SameSite=Lax OAuth correlation cookie. Navigate to `authorization_url`. The existing login cookie is retained. Flow expiry is ten minutes; one concurrent browser flow is supported.
- GET `/connections/:provider/callback?state=...&code=...` is public but validates single-use state, correlation cookie and the original still-active owner session. It stores encrypted destination candidates and redirects to `/settings?connection_flow=UUID`. Declined consent redirects with `connection_error=consent_declined`. Other failures return the normal safe error envelope.
- GET `/connection-flows/:id` → `{id,brand_id,provider,destinations:[{id,name,username:string|null}]}`. Requires the same owner session which started the flow.
- POST `/connection-flows/:id/complete` `{destination_id,timezone?:"UTC"}` → channel. Select one returned destination. Reconnect refuses a different external identity. Existing schedules/history remain attached to the original channel; a disconnected/paused channel stays paused until the owner resumes it.
- POST `/connections/bluesky` `{brand_id,identifier,app_password,reconnect_channel_id?:UUID|null,timezone?}` → channel after a provider identity check. App password is not retained; resulting session grants are encrypted. Both connection paths reject malformed or non-string reconnect IDs before storing a flow or contacting a provider.
- POST `/channels/:id/disconnect` `{confirm_shared_impact:true}` → `{disconnected:true,provider_revoked:false,channels_requiring_reconnection:number,revocation_id:UUID|null,next_action}`. Clients must warn **before** confirmation that the selected channel's queued deliveries are canceled, other connected channels for this provider including unrelated accounts may require reconnection, and provider access removal is manual. Missing or false confirmation returns `disconnect_confirmation_required` (400) before mutation. Disconnect pauses the selected channel and clears its credentials; it never sends a provider revocation. A known or possible grant requires owner removal, and returns a pending removal UUID. Until its confirmation the provider is fenced against new grants; other connected channels for that provider are marked for reconnection with their credentials, pause settings and queued work preserved. Active deliveries or replies on affected channels must resolve first; active syncs must finish. Already-disconnected channels with no stored grant are no-ops unless removal is pending. A busy provider returns a conflict advising a fresh status check, not removal instructions.
- GET `/connections/:provider/removal-status` → `{provider,revocation_id:UUID|null}`. This owner-only read also works when the app configuration is missing. It returns 409 while another provider operation owns the gate; wait and recheck before any manual removal. A null ID means no pending removal at the time of the read.
- POST `/connections/:provider/acknowledge-revocation` `{access_removed:true,revocation_id:UUID}` → `{revocation_acknowledged:true}` records the owner's attestation that manual access removal for that exact pending boundary is complete. A stale or mismatched UUID returns `revocation_id_conflict` (409) and cannot clear a newer boundary; refresh the owner-only app list before confirming. Attestation is not provider proof and does not claim removal has propagated.
- GET `/providers` now describes installed adapters with `{id,name,formats,oauth,analytics,inbox,reply,implementation,configuration,execution,verification,reason}`. Live verification remains `unverified_live` until separately qualified. A connection changes channel verification to `identity_verified_publishing_unverified`, not live publishing verified.
- Channel additionally exposes `{connection_identity:string|null,connection_status:"manual"|"connected"|"reconnect_required"|"disconnected",connection_error:string|null,connected_at:timestamp|null}`. Credentials never appear in channel responses.

Publishing options are immutable per-channel snapshot fields under `options`. Current adapter fields: Facebook `{format?:"reel"|"video"}`; Instagram `{format?:"story"}`; YouTube `{privacy:"private"|"unlisted"|"public",made_for_kids:boolean,contains_synthetic_media?:boolean,category_id?:string}`; Mastodon `{visibility?:"public"|"unlisted"|"private"|"direct",content_warning?:string,sensitive?:boolean}`; Threads `{reply_control?:"everyone"|"accounts_you_follow"|"mentioned_only"}`; Pinterest `{board_id:string,link?:string}`. Facebook formats select distinct one-MP4 paths. Instagram Story selects exactly one JPEG or MP4; its saved text, title and media descriptions are preserved locally and in the snapshot, but the provider receives none of them as a caption, overlay or alt text. Story stickers and other options are not supported. Google Business Profile accepts `{topic_type?:"STANDARD"|"EVENT"|"OFFER",language_code?:string,event?:{title,start_date,start_time,end_date,end_time},call_to_action?:{type:"BOOK"|"ORDER"|"SHOP"|"LEARN_MORE"|"SIGN_UP"|"CALL",url?:string},offer?:{coupon_code?:string,redeem_online_url?:string,terms_conditions?:string}}`. Topic defaults to STANDARD. Event/offer require event fields; dates are `YYYY-MM-DD`, times are `HH:MM` in the location’s local wall time, with end after start. Non-CALL actions need an HTTP(S) URL without credentials; CALL forbids one. OFFER forbids a CTA, and unknown fields are rejected. The adapter accepts text and zero/one JPEG/PNG photo and requires a public HTTPS origin for photos. Saved photo descriptions remain in the media library and immutable snapshot but are not sent to Google. The working title is internal; event titles use the explicit event option. The adapter rejects unsupported media formats instead of silently stripping them. Provider descriptions list current format limitations.

### Provider observations and recovery

- POST `/channels/:id/sync` `{allow_metered?:boolean}` → `{metrics_observed,inbox_items,coverage:"partial_recent_page",errors:string[],note}`. Requires `publishing:write`; X refuses reads unless `allow_metered:true` explicitly acknowledges costs. Fetches observations for at most ten local published posts and one recent inbox page (Meta: one page for each of at most ten local posts). No automatic paid polling.
- GET `/analytics` keeps the local `summary` and returns `availability:"unavailable"|"partial"`, `reason`, and `metrics:[{publication_id,channel_id,provider,text,external_url,observed_at,metrics:[{name,value}]}]`. Provider metrics are never synthesized from local workflow counts.
- GET `/inbox` returns `availability:"unavailable"|"partial"`, `reason`, `items:[{id,channel_id,channel_name,provider,item:{id,parent_id,author,text,url,created_at},read_at,synced_at,can_reply}]`. Render text as text, never raw HTML; Mastodon content may contain markup.
- POST `/inbox/:id/read` `{}` → `{ok:true}`.
- POST `/inbox/:id/reply` `{text,request_id:UUID}` → durable reply `{id,inbox_id,owner_id,text,state,receipt,error,created_at,updated_at}`. Reuse the same request ID when checking a lost response. The server never resends that ID. `state` is sending/published/failed/uncertain. Reply writes need `publishing:write` and can have real public effects.
- POST `/publications/:id/provider-reconcile` `{}` → updated publication if a provider receipt conclusively proves completion or a saved upload/job can safely resume; an inconclusive probe leaves it uncertain, and a failed probe can return an error. Probes cover YouTube resumable upload completion, Bluesky saved video jobs and deterministic record lookup, Facebook Reel/Page video status, Instagram Story container status and a saved Google Business Profile local post. A Story container's published status does not supply a missing media ID, so it stays uncertain. Google `LIVE`/`RECURRING` returns published; `REJECTED` returns failed; processing, scheduled, unknown and inconclusive reads stay uncertain. A pending Bluesky job can return the publication to `queued` without another upload. Absence of proof never marks not-published or creates a replacement post automatically.
- GET `/provider-media/:id?token=...` is an expiring provider-fetch capability URL, issued server-side for supported media publication. It must not be logged or shared. It is not the authenticated media library URL.

## Generated contracts

Core JSON handlers deserialize the Rust request types in `crates/server/src/contracts/requests.rs`; OpenAPI derives their required fields, UUID/date formats, and response structures from Rust. Generate the OpenAPI artifact and frontend types from this same source:

```sh
cargo run -q -p beweft-server --bin beweft-contract > docs/openapi.json
cargo run -q -p beweft-server --bin beweft-contract -- --typescript > web/src/lib/api-contract.generated.ts
```

`ApiOperations` maps each method/path to its typed request, response envelope, and query parameters. Binary media responses are explicitly represented as bytes/Blob. Invalid typed JSON returns 422; business validation returns 400. The HTTP integration runner checks actual response bodies against the served schemas.

Queue-slot daylight-saving policy: a nonexistent local time is skipped that day; a repeated local time uses the earlier occurrence only. Existing publications created before scheduling modes were recorded are conservatively retained as exact dates. Explicit rescheduling pins a publication to an exact date.

Local server binding defaults to `127.0.0.1:3000`; container deployments explicitly set `BEWEFT_BIND=0.0.0.0:3000`. HTTP request spans record method and path only, omitting OAuth query parameters. `BEWEFT_FIXTURE_DELAY_MS` is an opt-in fixture-only fault-injection delay (capped at four minutes), used to exercise real worker interruption/restart and independent heartbeat behavior.

Provider safety additions:

- Channel `capabilities.permissions` is `{source,reported_scopes,actions,note}`. Each action (`publish`, `media`, `metrics`, `inbox`, `reply`, plus Facebook `reel`/`video` or Instagram `story`) is `{status:"granted"|"missing"|"unknown",required_scopes:string[],missing_scopes:string[]|null}`. Capability implementation and observed scope grants are distinct. Unknown is not verified permission. Missing required scope blocks the corresponding operation. Existing direct Meta grants receive installed format and new-action descriptions on read, calculated from already reported scopes; the saved credentials and other capabilities are not rewritten. After refresh, `publishing` and the detailed grant status update together; `publishing:true` includes unknown grants and is not proof of access.
- Inbox `item.reply_context` is nullable `{visibility:string,recipients:{id:string,acct:string}[]}`. For Mastodon, private/direct sources produce direct replies only to these participants. Public/unlisted retain their visibility. The reply request body remains `{text,request_id}`; added `@` mentions are rejected.
- `GET /publications/{id}/provider-status` returns `{session_expired:boolean,reset_allowed:boolean,reason:string|null,x_upload:{phase:"upload"|"post_started",attempt_id:UUID,checkpoint_id:UUID,reset_allowed:boolean,reason:string}|null,meta_delivery:{phase:"upload"|"post_started",attempt_id:UUID,checkpoint_id:UUID,retry_allowed:boolean,reason:string}|null,linkedin_delivery:{phase:"upload"|"post_started",attempt_id:UUID,checkpoint_id:UUID,retry_allowed:boolean,reason:string}|null}` without exposing resumable URLs or credentials. The top-level reset fields describe YouTube; `x_upload` applies to X video, images and text. `post_started` means a public send may have started. Legacy X image checkpoints are conservatively treated as `post_started`; the upgrade assigns a stable observation identity (using an existing attempt where available). `meta_delivery` describes Instagram/Threads containers and Facebook Reel/Page video delivery; `post_started` includes accepted operations still processing. Its `retry_allowed` applies to the generic explicit retry, which archives and clears the old checkpoint. `linkedin_delivery` describes LinkedIn member media and text delivery. Its generic retry requires the owner to attest `not_published` using the current attempt/checkpoint IDs, `sender_stopped:true`, `provider_inspected:true` and a note; retry then archives the prior checkpoint identity and starts a new delivery. Neither an attestation nor a retry is automatic. Reload after a conflict.
- The same status adds `x_thread:null|{phase:"preparing"|"ready"|"request_started"|"complete",confirmed_ids:string[],next_index:number,total:number,remaining_texts:string[],attempt_id:UUID,checkpoint_id:UUID,root_request_started:boolean}` and `x_thread_retry_allowed:boolean`. `root_request_started` is true only for a current root checkpoint with explicit empty confirmed IDs and zero index; it is not proof of the remote outcome. `next_index` is zero-based; unconfirmed text might already be public. Retry is offered only after an explicit safe reset with no later attempts. Missing or malformed checkpoints do not prove that a post was absent.
- `POST /publications/{id}/provider-reconcile` additionally returns `{state:"uncertain",session_expired:true,reason}` for an expired YouTube session. This is not proof of nonpublication.
- `POST /publications/{id}/reset-x-upload` requires an owner session and `{observed_attempt_id:UUID,observed_checkpoint_id:UUID,sender_stopped:true,confirm_restart:true,provider_inspected?:boolean}`. The observation must still match under the channel/publication locks. Upload-only uncertain/failed checkpoints can be reset after the sender-stopped attestation. A `post_started` checkpoint additionally requires `provider_inspected:true` and a later recorded not-published attestation for the same IDs. The response is `{state:"failed",session_reset:true,next_action:string}`; reset never schedules, and a separate explicit retry is required. Generic retry refuses uncleared X checkpoints. The attestation does not prove an already accepted remote request was canceled.
- `POST /publications/{id}/reset-expired-session` requires an owner browser session, failed publication, expired-session receipt and a later owner `not_published` reconciliation. Returns `{state:"failed",session_reset:true,next_action:string}`; use the existing explicit retry action afterward. Otherwise 409. Reset never schedules a replacement automatically.

Worker integration: `provider_bridge::publish` requires the immutable publication JSON plus `attempt_id` containing the UUID already persisted by its current worker claim. All worker completion data, including provider IDs/URLs, must be committed through the same attempt-fenced completion transaction. Checkpoints are written only while that attempt remains sending with an unexpired lease. X upload progress and Bluesky video processing may yield to another claim; the finished attempt is `continued`, its original `scheduled_at` is retained, and a database-clock `not_before` respects processing delay. Bluesky automatic polling stops at a 30-minute database-clock deadline; provider reconciliation may query and resume the same saved job. A public-start checkpoint is never automatically executed under another attempt.

Durable reply recovery:

- `GET /inbox/{id}/replies` is read-only and returns an owner-scoped array of durable reply attempts `{id,inbox_id,text,state,revision,receipt,error,created_at,updated_at}`, newest first (up to 100). Sending attempts past their stored delivery deadline are projected as `uncertain`; reading never sends or mutates a reply. Load this before enabling a new reply, including after reopening a conversation or switching browsers.
- `POST /inbox/{id}/reply` reuses the supplied UUID for recovery. A fresh UUID receives 409 while **any** sending/uncertain attempt exists for that inbox item. The guard and claim are atomic under the channel lock, so concurrent tabs cannot bypass it.
- `POST /inbox/{id}/replies/{request_id}/resolve` requires an owner browser session and `{resolution:"published"|"not_published",observed_revision:integer,sender_stopped?:boolean,note:string,external_url?:string}`. The revision must match a freshly inspected history row. For not-published, `sender_stopped:true` is the owner's attestation that the original sender has stopped; the owner must also inspect the provider. This attestation is not proof of the remote outcome. An active local execution returns `reply_execution_active` (409) without waiting; a changed observation returns `reply_observation_changed` (409). Reload and inspect again after either conflict. Resolution accepts uncertain or expired sending attempts, records the attestation in the receipt and audit log, and returns the durable reply row. Published becomes `published`; not-published becomes `failed`. A new reply requires another explicit user action.

Reply-history watermark: a new `POST /inbox/{id}/reply` includes `expected_last_request_id: UUID|null`, taken from the first row of the latest acknowledged `GET /inbox/{id}/replies`, or null for empty history. Omitted means null and therefore requires empty history. Under the same claim lock, the server compares this watermark with the latest durable attempt before claiming a fresh UUID. A mismatch returns HTTP 409 with `error.code="reply_history_changed"`; refresh history and require explicit confirmation, never automatically retry with another UUID. Reusing an already stored request UUID returns its original result before the watermark check. History uses a durable insertion sequence, so lock waits and clock changes cannot make a newer claim appear older. The unresolved-attempt guard still applies independently.

Reply claim timing: new attempts store `created_at=clock_timestamp()` and an internal `delivery_deadline` 90 seconds after the actual claim. The server derives a suspend-inclusive elapsed budget from PostgreSQL's remaining time; lock waits and credential refresh do not count as time in flight. A live reply sender holds a nonblocking database execution guard through its outbound operation and completion. A closed database session or canceled transport does not prove that a provider did not receive an already-started request. Expiry and local guard release alone never prove a reply was absent remotely. Owner recovery must ensure the original sender is stopped and inspect the provider before recording not-published.

### Google Business Profile recovery and identity

- Connection flow `destinations[].id` is the discovered `accounts/{id}/locations/{id}` pair; `name` is the location and `username` identifies the selected account. Completion accepts only a returned encrypted candidate. The saved channel `connection_identity` is the stable `locations/{id}`; the selected parent remains encrypted. Reconnecting a different parent requires explicit selection of the same location.
- YouTube and Google Business Profile share the legacy YouTube OAuth generation, gate and removal marker. Either status or acknowledgment route addresses the same exact marker. Both app saves, starts, callbacks and completions are blocked while pending; old flows cannot cross the generation boundary. Disconnect checks in-flight work across both, cancels only the target's unsent queue, and marks connected siblings for reconnection while retaining their credentials and queues. Stop older API and workers before enabling this version.
- Provider status adds nullable `google_delivery` `{phase:"create_started"|"processing"|"rejected",attempt_id:UUID,checkpoint_id:UUID,post_name:string|null,retry_allowed:boolean,reason:string}`. The resource name is saved before follow-up reads; a lost create has no name. Neither a missing post nor a stopped local sender proves the remote operation ended.
- Google owner reconciliation requires the current attempt/checkpoint IDs, `sender_stopped:true`, `provider_inspected:true` and a note for either outcome. For not-published, inspection explicitly attests the remote operation definitively failed, stopped, or was canceled; if unknown, retain uncertain. A saved post name is used as the external ID for owner-published resolution. If no name was saved, an optional owner-supplied external ID must be a canonical `accounts/{id}/locations/{id}/localPosts/{id}` resource for the same location; it is owner attestation, not provider proof. A provider `REJECTED` receipt or matching owner not-published attestation permits a separate explicit retry, which archives the original identifiers. No provider call or retry follows from the attestation itself.
